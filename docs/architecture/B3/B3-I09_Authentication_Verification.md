**Error reconciliation.** The implemented security handlers use RFC 9457 with HTTP-matching status, code and traceId. Candidate operation-level error lists are incomplete. Common examples are VALIDATION_FAILED (400), AUTHENTICATION_REQUIRED (401), ACCESS_DENIED or ACCOUNT_DISABLED (403), and AUTH_STATE_UNAVAILABLE (503). Registration verification can return EMAIL_CONFLICT (409), and key registration or proof can return DEVICE_KEY_CONFLICT (409). Google challenge issuance can return AUTH_PROVIDER_UNAVAILABLE (503). Expired bearer tokens can be rejected by the filter before operation-specific diagnostics. The OTP cooldown implements 429. Per-operation abuse limits, remaining error-code mappings, and the final contract still require review. Flutter must handle unknown codes by HTTP status and never infer success from an error.

**Apple request discrepancy.** The executed Apple test sends `POST /auth/challenges` and observes 503. For provider exchange, the candidate Apple-native request requires `authorizationCode`. The current controller checks the allowed request fields before it dispatches by provider, and its allowlist omits that field. Source inspection therefore predicts 400 `VALIDATION_FAILED` for the candidate-shaped exchange request. This exchange result has no execution evidence in the accepted run. ## Replay evidence and retention

**PASS.** After A → B → C, reusing A returns 401 `REFRESH_TOKEN_REUSED`. C then returns `SESSION_REVOKED` and its access token loses authorization. After six rotations the test races A against rotation of the current token. If rotation wins the lock, even its newly issued successor loses refresh and access. Both cases check that exactly one family was revoked and the sibling device can still refresh. [Two- and six-rotation cases](../../../src/test/java/com/unispace/infrastructure/security/AuthenticationJourneyTests.java#L164) · [Atomic history write](../../../src/main/java/com/unispace/identity/persistence/SessionLifecycleRepository.java#L63) · [Committed replay revocation](../../../src/main/java/com/unispace/identity/application/SessionLifecycleService.java#L50) · [V2 digest history](../../../src/main/resources/db/migration/V2__authentication_security.sql#L138)

The stable family ID is auth_sessions.id. Rotation moves the old HMAC digest into a separate unique row in consumed_refresh_tokens while updating the session's current digest. Both changes commit together. The repository checks both indexes, locks the owning user and session, then rechecks history at READ COMMITTED. Each recognized replay revokes that family before returning the error, including if the account is disabled or the session expired. The FK restricts deletion of a referenced session. There is no purge job.

**Retention rule for this implementation:** retain every spent digest and its parent session. Never expire individual history rows by age while the family can remain valid. Sliding inactivity allows a family to outlive 30 days indefinitely. Preserve history and session state together in backup and recovery. Monitor table growth. Deletion for terminal families requires a separately approved retention period, consideration of incident and institutional obligations, and a rule preventing resurrection on restore. A cleanup job is outside I09. FR-155's audit-event retention is a separate obligation.

**Refresh HMAC key operations:** deploy one stable secret consistently to all instances. V1/V2 contain no key version, and the verifier currently uses one key. Swapping that key during a rolling deploy breaks recognition of old current and spent tokens. Old digests cannot be converted to new-key digests without the opaque credentials. Routine seamless rotation therefore requires separately reviewed multi-key lookup, continuity tests for current and historical tokens, and a retirement policy. Until then, a required emergency cutover must quiesce issuance/refresh on all instances, explicitly revoke all pre-cutover families, preserve history for incident review, switch every instance consistently, and require provider reauthentication. The new key alone cannot identify old-key replay. Restore procedures must preserve revocations and matching key material. This is an operational requirement, with no automated cutover or administrative endpoint.

## Verification boundary

On November 25, 2026, `.\mvnw.cmd -B -ntp test "-Dunispace.mysql.tests=true"` completed successfully using disposable MySQL 8.4 containers. Maven executed 118 tests. All 118 passed, with 0 failures, 0 errors and 0 skipped. This includes the 113 B3-I08 regression cases, four HTTP journey cases and one Google ID token regression that requires a string `sub` claim in the signed payload.

The I09 loopback tests use an embedded servlet server, disposable MySQL 8.4, the application Google verifier with a generated verification key, an in-memory mailbox, software P-256 client keys, and a test clock for UniSpace JWT expiry. Accounts, flows, OTPs, trust and sessions are created through HTTP. Test setup seeds the institution policy, and one test disables the user to observe immediate denial. Existing suites cover transactional rollback, concurrent OTP/proof consumption, and malformed credential handling. Production edge logging and mobile secure storage require deployment checks in addition to these application tests.
